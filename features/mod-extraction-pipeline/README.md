# Mod extraction pipeline: the recipe as code, with gates that fail closed

Status: built 2026-10-11, first customer FH. Tool:
`tools/bf1942-models/mod_pipeline.py`. Tests:
`tests/test_mod_pipeline.py`, `tests/test_regression_corpus.py`. Nothing here
publishes; publishing stays `scripts/publish-mesh-delta.py`, by hand.

## The owner's request

"The goal is to be able to have a framework in place to extract all maps with
high levels of confidence." Before this, the per-mod recipe was a throwaway
script outside the repo (`~/.cache/mod-bake/mod.sh`) and prose in memory notes;
steps were forgotten (deployables.json, menu music, voices, loadouts,
viewmodels, vehicle-ai, tree billboards, HUD packs), a subset re-extract
silently stripped the thumbs from `models.json`, a level re-bake lost its flag
cloth or its optimise pass, and the defects (silent trucks, floating guns, white
textures, a missing bolt animation, a tank sight, a crosshair block) were found
by the owner by hand.

## Run a new mod

```
cd tools/bf1942-models
# 1. add a ModConfig to mod_pipeline.MODS (id, install folder, kit flags, level_all)
python3 mod_pipeline.py steps --mod <Mod>                      # read the recipe it will run
python3 mod_pipeline.py run --mod <Mod> --all-own-levels --dry-run   # plan + read-only gates
python3 mod_pipeline.py run --mod <Mod> --all-own-levels \
    --scorecard-dir ../../features/mod-extraction-pipeline/scorecards
```

`run` is resumable: re-issue the same command after a failure and finished
steps are skipped (`--force-steps` redoes them, `--only-steps a b` and
`--from-step X` narrow it). Other entry points:

| Command | What it does |
|---|---|
| `steps --mod M` | print the ordered recipe with the commands it would run |
| `run --mod M [--levels L ...] [--dry-run]` | the steps, then the gates and the scorecard; `--dry-run` runs no extractor and writes no tree file |
| `verify --mod M` | only the idempotent verification steps, then the gates |
| `gates --mod M` | the gates and the scorecard; touches nothing but `out/` |
| `prose --write-readme` | regenerate the step table below from `STEPS` |

Options: `--jobs` (default 4), `--min-free-gb` (default 15; a step with a disk
guard has its process group killed below it, and a `--level-all` models pass is
skipped when its estimate would cross it), `--port` (default 5312; 5273 is
refused, it is the owner's), `--gates static render behaviour completeness
rules corpus`, `--behaviour-quick` (a sample, which can never earn a tier).
Anything that opens a browser runs under `flock /tmp/claude-1000/chromium.lock`
against a `serve_viewer.py` the pipeline starts and stops itself.

State and logs live in `tools/bf1942-models/out/mod-pipeline/<id>/` (gitignored),
not inside the asset tree: the mesh publisher walks the trees recursively and
would upload a state file. `--state-file` moves it.

## The recipe

Generated from `STEPS` (do not edit between the markers; run `prose
--write-readme`). Order is enforced by `tests/test_mod_pipeline.py`:
`after` names must precede, the manifest follows models, levels, kits and
viewmodels, thumbs follow the manifest, the manifest runs again after thumbs and
last, `kits` and `viewmodels` follow `levels` because they read `maps.json`,
`flag_cloth` and `optimise` follow the bakes, and every `extract_*.py` in the
folder is either a step or listed in `NOT_A_STEP` with the step that runs it.

Verification steps (`verify`, idempotent):

* `v_outputs`: Every step's declared outputs exist with their minimum counts
* `v_counts`: mods.json counts equal models.json / maps.json / poses on disk
* `v_gz`: Every glb has a fresh .glb.gz beside it (the publisher refuses otherwise)
* `v_thumbs`: Every models.json entry names a thumb that exists
* `v_levels`: Every baked level has its kits, loadouts, loading block, first-person skins and a fresh scene.glb.gz: what a level bake alone never writes
* `v_static`: The fast static audits (audit_mod.py: kits, vehicles, words, data, models, sound, completeness, animation, placement, textures, hud, poses, levels; no browser, one process each) finish, and no play-breaking finding is open: no kit, cannot use a weapon, cannot toggle, cannot drive
* `v_harness`: The viewer's fast node harnesses (flight, collision, control points, audio, hand fire, seats; HARNESS_TESTS, about 25 s) pass

Per-mod flags are in `MODS`: FHSW and FHSWEurope run no `--level-all` (its
reskin glbs wrote 60,433 files and filled the disk on 2026-09-30). Every tree
exports its kit pickups, one glb a distinct bag (FHSW: 189 for 1,185 kits,
+17 s and +24 MB before the texture store); until 2026-10-17 FHSW and
FHSWEurope ran `--no-pickups`, carried over from the service record's
poses-only tree, and a dead man's kit lay invisible in the map page. Desert
Combat and DC Final add `poses_matrix` (`--matrix --export --split-only
--soldiers <from kits.json>`). The voice languages are the chain's own
(2026-10-17): every `setRadioLanguage` its soldiers declare is extracted, in
the folder `extract_capture_voices.LANGUAGE_NATIONS` names or, for a language
the table lacks, its name lower-cased (bf1918's `austrian`, `senegal`), and
each line is read from the path the mod's own script loads it from
(`Sound/@RTD/Battlefield1918/Soldiers/@Language/` in bf1918). The static
audit's `voices-tree-stale` names a tree whose manifests differ from what the
extractors would now write.

`kits` and `collision` take `-j` (2026-10-12). Both spent their run loading
levels one after another, a level's load being the chain's `objects/` read
again behind that level's scripts (9.4 s on FHSW): `collision` loads every
level of the chain for the vehicles it declares itself (165 loads, 1,688 s of
1,717 s), `kits` every level that binds a kit the baked levels bind, for its
own copy of it (80 loads, 776 s of 818 s). With `-j 20` on this PC (20
threads, 62 GB) FHSW's `collision` takes 273 to 321 s and `kits` 139 to 146 s
over repeated runs, each peaking near 21 GB across its workers, and each
writes the files a serial run writes, byte for byte. The workers are forks of
the extractor (`extract_models.forked_workers`), so none builds the chain's
library or the census again; each holds one level's load (0.9 GB on FHSW),
and `memory_capped_jobs` starts fewer of them when `MemAvailable` would not
hold that many. `kits` still reads every level's scripts under `--maps`:
restricting its census to the baked levels (`read_chain_levels(only=)`, as
`extract_loadouts.py` does) takes FHSW to 31 s and 4.7 GB, and drops the
`levelVariants` rows that name a level outside `maps.json` (41 of them, on 25
kits) with their 13 `<Part>@<Level>` glbs, so it is not done.

### Adding levels to a baked mod (2026-10-13)

The owner's report: agents asked to extract the next ten FHSW maps baked the
scenes and forgot the kits, models, sounds and everything else a level needs.
The pipeline had codified that forgetting. A step recorded `done` with an
unchanged command was skipped, and no step's command names the levels except
`levels` itself, so `run --levels New` baked the scene and skipped kits,
loadouts, viewmodels, loading, hud, poses and the registry as finished. On the
morning of 2026-10-13, 17 of FHSW's 50 baked levels had no first-person paint
(`viewmodels/skins.json`) and 4 of FH's 10 were bound by no kit; most of those
levels had been baked by hand with `extract_maps_all.py --levels`.

Now a `Step` declares `inputs`: the manifests whose SET is part of its
up-to-date check (the level directories of `maps.json`, the kits with the
levels each binds of `kits.json`, the names of `models.json`). Other keys of
those files, a `loading` block or a `thumb`, are not the set, so the step that
rewrites them does not stale every reader. A changed set re-runs the step and
the plan says why: `would-run (inputs changed: viewer/maps/mods/fhsw/maps.json)`.

Three more things the same morning changed:

* `levels` passes `--skip-existing` unless the run is `--force-steps`. A `run`
  with no `--levels` over a tree whose levels were baked by hand completes it
  (the baked set is read from `maps.json`) instead of re-baking fifty scenes;
  an exporter fix re-bakes with `--force-steps`.
* `--no-gates` stops after the verification steps: completing a tree without
  the hours of audits, which `gates --mod M` runs afterwards.
* `v_levels` lists, per baked level, what a bake alone never writes: a loading
  block, a kit that binds it, a `loadouts.json` entry, first-person paint, a
  fresh `scene.glb.gz`. A level in any of its lists is not done.
* A step may tolerate an exit code with a `done_marker`: `viewmodels` exits 1
  for a pair whose clip the install does not hold (FHSW's GeballteLadung and
  fifteen more) and had stopped the recipe before the registry and the
  thumbnails twice; with the extractor's own closing line in the log and the
  outputs verified it is `done-with-findings`, and a crash, which prints no
  marker, is still a failed step.

`--pick N` (and the `pick` subcommand, which only prints) chooses the next N
of the mod's own levels not yet in the tree: the ones that ship single-player
data first, alphabetical (the game's own rule for listing a level under
Instant Battle, and the only levels a bot can be put on), the rest in a random
order `--seed` repeats; `--pick-random` drops the preference. The choice is
printed and appended to the state file under `picks`. On 2026-10-13 FHSW had
93 unbaked own levels, 10 of the first pick all single-player.

The procedure around the command (pre-flight, reading the plan, the stats-site
half, publishing, what done means, where each mod is tracked) is skill
`bf1942-mod-pipeline`, `.claude/skills/bf1942-mod-pipeline/SKILL.md`.

### Delta re-runs: one level no longer re-extracts the mod (2026-10-19)

The inputs mechanism above made a level addition re-run the right steps — and
two of them re-ran from scratch. Measured 2026-10-19, adding `rush_to_baghdad`
to FHSWEurope rebuilt 3,532 of 3,537 `.fp.glb` rigs (~1.5 h at `-j 10`) plus a
19-min whole-mod kit-poses pass, for a handful of new (soldier, weapon) pairs,
and since the outputs are deterministic almost every rebuilt file was
byte-identical to the one it replaced.

`extract_viewmodel.py` and `extract_pose.py --kit-poses` now take `--delta`:

* **Pair diff.** The required pairs are computed exactly as the full run
  computes them (`kit_pair_levels` over kits.json + maps.json + loadouts.json);
  a pair whose outputs are already on disk under its exact spelling is kept
  (`split_existing_pairs`: the `.fp.glb` and its report; `kit_pose_reuse`: the
  `.pose.glb`, its report and a clean `poses-matrix.json` row, which stands in
  for the export's and gets its kit list re-annotated). Only the missing pairs
  are built — a previously failed pair left no file, so it is retried and
  reports the same finding.
* **Index merge, never narrowing.** `viewmodels/index.json` and the poses
  `index.json` are rebuilt from the directory; `poses-matrix.json` and
  `gaits/gaits.json` merge as they always did (`gaits.json` now writes with
  sorted keys, so a tree grown level by level equals one written in one run).
* **Level skins.** `write_level_skins` still runs the full
  `expected_level_skins` decision pass over every level — a new rig image an
  old level repaints must reach that level's skin — but rebuilds a skin glb
  only when the level's expected textures differ from its previous row
  (`skin_row_reusable`); an unchanged level keeps its row and its glb.
* **Full stays the default, and the pipeline decides.** `--delta` is passed by
  `mod_pipeline.py` only when the step's prior record is `done` under the very
  same command and it re-runs because an input set or an output moved
  (`wants_delta`, `Step.delta_flag`); the plan prints `would-run (inputs
  changed: ...) [--delta]`. `--force-steps`, a changed command, a failed prior
  or no state record take the full pass — the delta trusts what is on disk only
  while this extractor and chain are what wrote it. The recorded command hash
  is the base command's, so a delta re-run does not stale the next plan.

The correctness gate is byte-identity: build a tree at N levels in one full
run, build it again as N-1 full + one `--delta` run, and every file — rigs,
poses, reports, skin glbs, `.glb.gz`, the texture store, every index — must
hash the same. Measured on GCMOD (own levels `GC_Alaris_Prime`,
`GC_Anchorhead`, then adding `GC_BCanyon`), `-j 10`, this PC:

| Step | One-level add before (full re-run) | After (`--delta`) | Byte-identity |
|---|---|---|---|
| `viewmodels` (205 rigs at 3 levels; the add brings 25 new) | 83 s | 16 s (5.2x) | 668 files sha256-identical; full-vs-full baseline also identical |
| `poses_kit` (205 poses; the add exports 21, keeps 184) | 147 s | 34 s (4.3x) | 740 files sha256-identical |

What is left in the delta's 16 s / 34 s is the fixed prefix both modes pay:
the chain's pools and library, the state machine, and (for the poses) the
kit sweep over the mod's own levels — on a big mod that prefix is minutes, not
the hour-and-a-half of rig rebuilds, since on FHSWEurope's scale the same
arithmetic turns the 3,532-rig pass into the handful of pairs a level actually
adds. Guards: `tests/test_delta_extract.py` (the pair diff, the skin-row reuse
rule, the matrix-row reuse rule, and the `wants_delta` wiring end to end on a
fake step).

### Parallel steps and CPU use (2026-10-13)

The runner starts steps side by side. A step waits for every step it is `after`,
and never runs beside one it shares a lock with (`step_locks`: `models.json`,
the glbs it writes or reads, the shared `_shared/sounds`, and any single file it
writes). Steps run while the cores they keep busy (`-j {jobs}`, or one) stay
within the CPU count plus 25%; a full-width step runs alone. The first failure
starts nothing new. `tests/test_mod_pipeline.py::ParallelSchedule` checks the
overlap, the order, the locks and the budget.

What changed inside the extractors, each checked for byte-identical output
against the serial run:

| Work | Before | After | Check |
|---|---|---|---|
| Vehicle sound table (2,463 vehicles, `extract_vehicle_sounds.py`) | 1,877 s serial | 249 s at 12 workers (7.5x) | 1,122 files byte-identical |
| Seat poses (123 poses, 3 soldiers, `extract_pose.py --seat-poses`) | 80.6 s serial | 25.6 s at 8 workers (3.2x) | 236 files byte-identical, same log |
| Viewmodel rigs (8 pairs; 17 files) | serial | forked workers, `-j` | byte-identical |
| FHSW `models` step (4,091 templates, `extract_all.py -j 20`) | 77.6 min at `-j 4` | 70.8 min at `-j 20`, before the seat-pose change | not re-run with it |
| 150-template model sample | 295 s at `-j 4` | 216 s at `-j 20` (1.37x) | outputs compared by run |

Limits found, and what they mean:

* The model export at `-j 20` is not 5x `-j 4`. On the 150-template sample the
  CPUs were saturated for about 110 s, after a 25 s serial prefix (the parent
  builds the library) and a 90 s tail where five or six workers ran the last
  heavy tanks (Panther, E-75). Each worker also rebuilds the library, about 26
  CPU-seconds apiece. `heaviest_first` starts the templates with the most
  triangles in their last bake first; it did not shorten the tail on the sample,
  because the slow ones are slow for reasons the triangle count does not show.
* The parallel model path and the serial one build different pools when
  `--level` or `--level-all` is given: the parent adds each level archive's
  objects and textures (`objects.add`), the workers do not. Changing workers to
  fork from the parent would change the output for those mods, so it was left
  alone. This needs a decision before anyone relies on the two paths agreeing.
* Each viewmodel worker holds about 107 MB of its own memory at peak; the
  1.1 GB chain is shared by fork. `PER_WORKER_BYTES` is 400 MB, a margin.
* A level bake peaks at 1.76 GB (Arctic_Convoy-1942, FHSW, 252 s). The level pool
  is capped at 2 GB per level by free memory (`PER_LEVEL_BYTES`).
* `thumbs` stays at `-j 2`: `shoot.mjs -j` is pages inside one Chromium, and
  the one-browser rule is the owner's. Its speed on a fresh bake is not measured.

### Two rules that were failure modes

* A subset model re-extract never writes `models.json`. Use
  `reextract_models_subset(ctx, [templates])`: it runs `extract_models.py` into
  a scratch directory, copies only changed per-template files, merges only
  those templates' rows and keeps every thumb key. A full `models` step runs
  inside `ThumbGuard`, which puts back any thumb key the extractor dropped
  whose file still exists. Then run `optimise` (textures to the shared store).
* After a level re-bake, `flag_cloth` and `optimise` are steps, not memory.

### Static validation on every run: `v_static` (2026-10-15)

`run` and `verify` end with a sixth verify step, `v_static`. It needs no
browser and no `--gates`. It runs `audit_mod.py`'s file-parsing audits, one
process each and all at once: kits, vehicles, words, data, models, sound,
completeness, animation, placement, textures, hud, poses and levels. On
FHSWEurope's 66 levels it took 4.9 min wall before hud, poses and levels were
added; on FHSW's 104 levels it takes 6.9 min with them (2026-10-16), set by
textures and placement.

* It fails on an open play-breaking finding (`audit_mod.PLAY_BREAKING`),
  which it lists first: no kit look, cannot use the weapon, cannot toggle,
  cannot fire, aim or drive.
* It fails on an audit that did not finish.
* Visible-defect blockers, majors and minors are counted. They do not fail
  the step.
* Mod data is `ACCEPTED` with its reason.

Findings are written to `out/mod-pipeline/<id>/static/`: one `<audit>.json`
per audit, plus `summary.json`. `--no-static` skips the step, and so does
`--dry-run`. Why the step exists, and what it covers of the defects the owner
has found, is in `features/static-validation-coverage`.

### Behaviour on every bake: `v_behaviour_new` and `v_harness` (2026-10-15)

Owner decision: a `run` that bakes new levels drives them in a headless page
before it is done. `v_behaviour_new` is the last step of the recipe, after
`manifest_final`. It runs `audit_behaviour.mjs --quick` over the new levels
only, about 5-10 min a level. The quick run covers kits (select, fire,
alt-fire, reload, rig and barrels, firing the primary weapon only), spawns
and seat spawns, two flags, and one vehicle of each kind (enter, drive,
steer, turret, held W/S axes, fire, sounds, exit, wreck). It also runs 20 s of
bots and catches page errors and 404s.

* **New** means the `--levels` / `--pick` / `--all-own-levels` names that
  `maps.json` did not list before the run, when the run's `levels` step runs.
  With `--force-steps`, every level the step re-bakes counts. A run that
  bakes nothing checks nothing. The set is kept in the state file under
  `behaviour_new.pending` until a check of it passes. A resumed run still
  checks it, and so does the catch-up `run` after a scoped
  `--only-steps levels ...` re-bake. `--only-steps v_behaviour_new --levels L`
  checks L without baking it.
* **How it runs:** `serve_viewer.py` on the first free port in 5350-5359
  (never 5273), the audit under `flock /tmp/claude-1000/chromium.lock`, then
  the server stops. Level names go to the audit as one argv entry, so a name
  with an apostrophe is safe. It reuses `gate_behaviour`.
* **Verdict:** the step fails on any open blocker or major. Findings that
  `audit_behaviour_accepted.json` covers, or that the static audit explains,
  do not count. The step also fails on exit 2 (could not stage), on a missing
  JSON or a timeout (30 min a level), and on a new level the audit never
  reported. The report lists play-breaking causes first
  (`BEHAVIOUR_PLAY_BREAKING`), then the other blockers, then the majors.
  Output is `out/mod-pipeline/<id>/gates/behaviour-new.json`, with
  `.summary.json` and `.log` beside it.
* **What it is not:** a `--quick` run is a sample, and it never earns a
  scorecard tier. The full sweep stays under `gates`.
* **Opt-out:** `--no-behaviour-new` skips the step and leaves the levels
  pending. `--dry-run` prints the set it would check.

`v_harness` is a seventh verify step. It runs the viewer's fast node
harnesses in one unittest process: `HARNESS_TESTS`, 34 modules covering
flight, collision and ground, control points, audio, hand fire, and seats and
held axes. That is 621 tests in 25 s on this PC. It runs where `v_static`
runs, and `--no-static` skips both. It leaves out `test_nav_baked` (146 s),
`test_sim_vehicles` (96 s) and `test_mod_pipeline`. All 215 node-harness
modules together take 6.4 min.

### Proposed: cheaper republishing of a data-only change (2026-10-17)

Not built; written down for when the next data-only change lands.

FHX-21 added a few KB of JSON per gun (`projectile.depots`) and cost a
22 GB publish: the gun's spec lives in node extras inside every level
`scene.glb` that places it, and the publisher sends whole files. 159 exported
scenes (93 FHSW, 61 FHSWEurope, 5 FH) went up again at about 2 MB/s, roughly
3 hours, for byte-identical geometry and textures. The in-place patchers
(`patch_held_axes.py`, `patch_engine_limits.py`, `patch_round_depots.py`)
all have this shape: the JSON chunk changes, the BIN chunk does not.

1. **A JSON-chunk delta in `scripts/publish-mesh-delta.py`.** When a glb's
   BIN chunk is unchanged from what the volume holds (hash the BIN alone),
   send only the new JSON chunk and splice it into the file on the pod, then
   rewrite its `.gz` there. Helps every in-place patcher at once. Check first
   that the FileBrowser pod has what a splice and a gzip need; if not, ship a
   small static helper with the stream. Today's send would have been a few MB.
2. **Per-template weapon data in a shared table.** A tree-wide
   `_shared/weapons.json` keyed by FireArms template (round, magazine, depots,
   sounds), merged onto each gun group at load, as `vehicle-sounds.json` is
   for sounds. A weapon change becomes one file per tree, and no scene or model
   glb is rewritten. Costs an `assemble.py` change, the gun-group loader, a
   fallback for glbs that still carry the extras, and one last full publish.

A third cost seen the same day: `patch_scene.py --layer sounds --all` took
97 min on FHSW and 67 min on FHSWEurope to rewrite nothing but
`vehicle-sounds.json` (every level re-read its sound scripts and found them
unchanged). Building the shared table once, before and apart from the
per-level pass, would take the table change down to the table's own few
minutes.

## The gates

`run`, `verify` and `gates` end by running the audits as subprocesses and
merging them into one scorecard (per level, per mod; markdown in
`scorecards/`, JSON in `out/mod-pipeline/<id>/`).

| Gate | Source | What it is |
|---|---|---|
| `static` | `audit_mod.py --audit textures placement sound models data` | untextured, white, magenta, NaN or constant UVs; floating, buried or stacked objects; silent vehicles and weapons; models, kits, icons, thumbnails, viewmodels; data that resolves nowhere |
| `render` | `audit_render.mjs --levels` | every placed vehicle and three frames per level read back from the 3D canvas, flagged for white, magenta or black shares |
| `behaviour` | `audit_behaviour.mjs --levels <the run's levels>` | drives, flies, fires every vehicle and kit a level offers, spawns, flags, bots. Budget `BEHAVIOUR_LEVEL_TIMEOUT_S` (7,200 s) a level; a sweep out of time keeps the levels it finished and leaves the rest `unverified` |
| `completeness` | `audit_mod.py --audit completeness` | what the viewer, the play front end and the mod's own files call for that was never extracted, with the owning script |
| `rules` | in-process, `bf42.level` against the install | scene.json's capture-rule fields equal the raw ControlPointTemplates of the ROOT script's layer (all 15 fields, every mode); tickets equal the ROOT script's (TKT-3); every baked game type has a `GameTypes/` file (the server starts it); the loading screen and its music resolve in the tree; every spawner's vehicle resolves in models.json, a kit pickup or a node of the level's scene.glb; every kit a level deals is in kits.json |
| `corpus` | in-process probes over the tree | the regression corpus below |

A gate that is not installed, did not produce its JSON, crashed, or was a
`--quick` sample is reported as such (`not-installed`, `failed-to-run`,
`partial`) and can only make a level `unverified`.

Beside the gates, one audit runs against the **live site**, driven by what
real players shared rather than by what a bake wrote:

```
flock /tmp/claude-1000/chromium.lock \
  node audit_replay_assets.mjs --recent 3 --json out.json \
       [--recording <slug|/stats/recordings/x.ndjson|map.html url>]... \
       [--base https://play.bfstats.io] [--local <viewer dir>] \
       [--accepted audit_replay_assets_accepted.json] [--speed 30]
```

It plays each recording forward headless on `map.html` and keeps every
response of 400 or worse, classified by owning extractor (model / cockpit /
wreck / level-paint variant / kit pose / first-person rig / sound / level
bake / shared tree / texture or glb store) and split live-vs-local: a file
present under `--local` but 404 live is minor `asset.unpublished` (publish
pending), one absent locally too is major `asset.extraction-gap` (the
pipeline missed it; exit 1). A cockpit or wreck the models manifests say was
never exported (no `cockpit`, no `variants` row of configuration `wreck`) is
an `asset.optional-probe` info row — the page probes both for every flown or
destroyed hull — and a probe of a template no manifest lists at all follows
its base model's gap (`asset.follows-base-gap`, minor). The mod tree's and
vanilla's 404s for one file collapse to one finding naming both probed trees.
Findings carry `check` + `cause_key` + `template_or_kit` + `path`, and
`audit_replay_assets_accepted.json` matches them the same way the behaviour
audit's accepted file does (each row carrying `evidence`; seeded 2026-10-19
with the geometry-less fire-event weapons — bayonets, artillery spotters —
whose prop probes can never resolve). The classifier and severity routing are
pinned without network or browser by `tests/test_audit_replay_assets.py`
(`replay_assets_harness.mjs`).

The audit's first run (2026-10-19, the three newest feed recordings, all
FHSWEurope) found no unpublished files and three real gap families: the

steps' recorded commands.

### Tiers

| Tier | Meaning |
|---|---|
| `ready` | every required gate ran over this level; no blocker or major outside accepted-with-evidence; no minor |
| `ready-with-notes` | as above, but there are minors, or an open mod-wide blocker/major that cannot be tied to this level |
| `blocked` | an open blocker or major; the scorecard names `cause_key`, the evidence and the owning script |
| `unverified` | a required gate did not run for this level, is not installed, or failed to run. Beats `blocked`. Never counts as ready |

Findings reach a level by its name, or, for a mod-wide finding about a template
(`Tiger.glb`), because the level places that template. `level-not-extracted`
(completeness) is listed and sets no tier: an unbaked level does not make a
baked one worse, and what is exported is the owner's call. A finding on a
baked level the run did not gate (the tree-wide static audit raises them)
reaches no level and no tier; the markdown counts them. Until 2026-10-20 such a
finding was charged to every gated level placing the same template (Pasir
Panjang's sampans blocked Java). A `retail_faithful: true` claim without non-empty evidence stays an
open finding; with evidence it is listed under "Accepted exceptions" with the
text, so a human can review every exception in one table.

## What the tier means, and what it does not catch

A `ready` level has been through six independent readers, none of which is a
person playing it. What the framework does catch: anything that shows as a
missing, white, magenta or black pixel in a still; a texture, sound, kit,
icon, viewmodel, thumbnail or model that does not resolve; a vehicle that will
not drive, fly or fire in the headless page, a kit that cannot spawn or fire,
a flag that cannot be taken; a baked rule that differs from the script it was
read from; a step of the recipe that did not run or wrote too little; the
defect classes in the corpus returning.

What it does not catch, and the tier makes no claim about:

* **Feel.** Recoil, handling, flight model, vehicle and soldier speed, camera
  shake, hit feedback, the bot difficulty. The behaviour sweep proves a vehicle
  moves, not that it moves like the retail one; the physics are ported and
  harness-tested elsewhere (`features/bf1942-engine-reference`), not re-judged
  here.
* **Retail-vs-viewer differences only the real game shows.** Mix levels of
  ambience and engine sounds, the exact tone of fog and water, lens flare,
  particle density, how a given animation reads. The render gate flags
  "mostly white/magenta/black", not "slightly wrong colour".
* **Behaviour classes not exercised**: the whole of multiplayer and the room
  server, the replay viewer on a mod's recordings, CTF, TDM and SinglePlayer
  rounds (the layers are baked and read for rules; no round is played in them),
  the radio, commander and artillery calls, parachute and bail-out sequences,
  every weapon in every stance, damage and wreck states below the first hit,
  vehicles that only exist in a level's script (carriers' deck traffic,
  ship-to-ship fire).
* **Anything the install does not contain.** A texture or sound absent from the
  retail archives is accepted with evidence (retail draws it untextured or
  silent too); the framework cannot tell a content gap in the mod from a bug in
  the viewer where the game itself degrades.
* **A gate that is wrong.** The audits are written against known defects. A
  new defect class passes until someone finds it and adds a check; add it to
  `REGRESSION_CORPUS` the day it is fixed.
* **Publishing.** Nothing here looks at the cluster or the published tree.
