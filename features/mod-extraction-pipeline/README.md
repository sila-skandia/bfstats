# Mod extraction pipeline: the recipe as code, with gates that fail closed

Status: built 2026-10-11, first customer FH. Tool:
`tools/bf1942-models/mod_pipeline.py`. Tests:
`tests/test_mod_pipeline.py`, `tests/test_regression_corpus.py`. Nothing here
publishes; publishing stays `scripts/publish-mesh-delta.py`, by hand.

## The owner's request

"The goal is to be able to have a framework in place to extract all maps with
high levels of confidence." Before this, the per-mod recipe was a throwaway
script outside the repo (`~/.cache/mod-bake/mod.sh`) and prose in memory notes;
steps were forgotten (deployables.json, menu music, voices, loadouts,
viewmodels, vehicle-ai, tree billboards, HUD packs), a subset re-extract
silently stripped the thumbs from `models.json`, a level re-bake lost its flag
cloth or its optimise pass, and the defects (silent trucks, floating guns, white
textures, a missing bolt animation, a tank sight, a crosshair block) were found
by the owner by hand.

## Run a new mod

```
cd tools/bf1942-models
# 1. add a ModConfig to mod_pipeline.MODS (id, install folder, kit flags, level_all)
python3 mod_pipeline.py steps --mod <Mod>                      # read the recipe it will run
python3 mod_pipeline.py run --mod <Mod> --all-own-levels --dry-run   # plan + read-only gates
python3 mod_pipeline.py run --mod <Mod> --all-own-levels \
    --scorecard-dir ../../features/mod-extraction-pipeline/scorecards
```

`run` is resumable: re-issue the same command after a failure and finished
steps are skipped (`--force-steps` redoes them, `--only-steps a b` and
`--from-step X` narrow it). Other entry points:

| Command | What it does |
|---|---|
| `steps --mod M` | print the ordered recipe with the commands it would run |
| `run --mod M [--levels L ...] [--dry-run]` | the steps, then the gates and the scorecard; `--dry-run` runs no extractor and writes no tree file |
| `verify --mod M` | only the idempotent verification steps, then the gates |
| `gates --mod M` | the gates and the scorecard; touches nothing but `out/` |
| `prose --write-readme` | regenerate the step table below from `STEPS` |

Options: `--jobs` (default 4), `--min-free-gb` (default 15; a step with a disk
guard has its process group killed below it, and a `--level-all` models pass is
skipped when its estimate would cross it), `--port` (default 5312; 5273 is
refused, it is the owner's), `--gates static render behaviour completeness
rules corpus`, `--behaviour-quick` (a sample, which can never earn a tier).
Anything that opens a browser runs under `flock /tmp/claude-1000/chromium.lock`
against a `serve_viewer.py` the pipeline starts and stops itself.

State and logs live in `tools/bf1942-models/out/mod-pipeline/<id>/` (gitignored),
not inside the asset tree: the mesh publisher walks the trees recursively and
would upload a state file. `--state-file` moves it.

## The recipe

Generated from `STEPS` (do not edit between the markers; run `prose
--write-readme`). Order is enforced by `tests/test_mod_pipeline.py`:
`after` names must precede, the manifest follows models, levels, kits and
viewmodels, thumbs follow the manifest, the manifest runs again after thumbs and
last, `kits` and `viewmodels` follow `levels` because they read `maps.json`,
`flag_cloth` and `optimise` follow the bakes, and every `extract_*.py` in the
folder is either a step or listed in `NOT_A_STEP` with the step that runs it.

* `v_outputs`: Every step's declared outputs exist with their minimum counts

Per-mod flags are in `MODS`: FHSW `--no-pickups` and no `--level-all` (its
reskin glbs wrote 60,433 files and filled the disk on 2026-09-30); Desert
Combat and DC Final add `poses_matrix` (`--matrix --export --split-only
--soldiers <from kits.json>`); a mod language missing from
`extract_capture_voices.LANGUAGE_NATIONS` extracts no voices (the `voices` step
fails its output check, which is how it is noticed).

### Two rules that were failure modes

* A subset model re-extract never writes `models.json`. Use
  `reextract_models_subset(ctx, [templates])`: it runs `extract_models.py` into
  a scratch directory, copies only changed per-template files, merges only
  those templates' rows and keeps every thumb key. A full `models` step runs
  inside `ThumbGuard`, which puts back any thumb key the extractor dropped
  whose file still exists. Then run `optimise` (textures to the shared store).
* After a level re-bake, `flag_cloth` and `optimise` are steps, not memory.

## The gates

`run`, `verify` and `gates` end by running the audits as subprocesses and
merging them into one scorecard (per level, per mod; markdown in
`scorecards/`, JSON in `out/mod-pipeline/<id>/`).

| Gate | Source | What it is |
|---|---|---|
| `static` | `audit_mod.py --audit textures placement sound models data` | untextured, white, magenta, NaN or constant UVs; floating, buried or stacked objects; silent vehicles and weapons; models, kits, icons, thumbnails, viewmodels; data that resolves nowhere |
| `render` | `audit_render.mjs --levels` | every placed vehicle and three frames per level read back from the 3D canvas, flagged for white, magenta or black shares |
| `behaviour` | `audit_behaviour.mjs --levels all` | drives, flies, fires every vehicle and kit a level offers, spawns, flags, bots |
| `completeness` | `audit_mod.py --audit completeness` | what the viewer, the play front end and the mod's own files call for that was never extracted, with the owning script |
| `rules` | in-process, `bf42.level` against the install | scene.json's capture-rule fields equal the raw ControlPointTemplates of the ROOT script's layer (all 15 fields, every mode); tickets equal the ROOT script's (TKT-3); every baked game type has a `GameTypes/` file (the server starts it); the loading screen and its music resolve in the tree; every spawner's vehicle resolves in models.json, a kit pickup or a node of the level's scene.glb; every kit a level deals is in kits.json |
| `corpus` | in-process probes over the tree | the regression corpus below |

A gate that is not installed, did not produce its JSON, crashed, or was a
`--quick` sample is reported as such (`not-installed`, `failed-to-run`,
`partial`) and can only make a level `unverified`.

### Tiers

| Tier | Meaning |
|---|---|
| `ready` | every required gate ran over this level; no blocker or major outside accepted-with-evidence; no minor |
| `ready-with-notes` | as above, but there are minors, or an open mod-wide blocker/major that cannot be tied to this level |
| `blocked` | an open blocker or major; the scorecard names `cause_key`, the evidence and the owning script |
| `unverified` | a required gate did not run for this level, is not installed, or failed to run. Beats `blocked`. Never counts as ready |

Findings reach a level by its name, or, for a mod-wide finding about a template
(`Tiger.glb`), because the level places that template. `level-not-extracted`
(completeness) sets the mod tier only: an unbaked level does not make a baked
one worse. A `retail_faithful: true` claim without non-empty evidence stays an
open finding; with evidence it is listed under "Accepted exceptions" with the
text, so a human can review every exception in one table.

## What the tier means, and what it does not catch

A `ready` level has been through six independent readers, none of which is a
person playing it. What the framework does catch: anything that shows as a
missing, white, magenta or black pixel in a still; a texture, sound, kit,
icon, viewmodel, thumbnail or model that does not resolve; a vehicle that will
not drive, fly or fire in the headless page, a kit that cannot spawn or fire,
a flag that cannot be taken; a baked rule that differs from the script it was
read from; a step of the recipe that did not run or wrote too little; the
defect classes in the corpus returning.

What it does not catch, and the tier makes no claim about:

* **Feel.** Recoil, handling, flight model, vehicle and soldier speed, camera
  shake, hit feedback, the bot difficulty. The behaviour sweep proves a vehicle
  moves, not that it moves like the retail one; the physics are ported and
  harness-tested elsewhere (`features/bf1942-engine-reference`), not re-judged
  here.
* **Retail-vs-viewer differences only the real game shows.** Mix levels of
  ambience and engine sounds, the exact tone of fog and water, lens flare,
  particle density, how a given animation reads. The render gate flags
  "mostly white/magenta/black", not "slightly wrong colour".
* **Behaviour classes not exercised**: the whole of multiplayer and the room
  server, the replay viewer on a mod's recordings, CTF, TDM and SinglePlayer
  rounds (the layers are baked and read for rules; no round is played in them),
  the radio, commander and artillery calls, parachute and bail-out sequences,
  every weapon in every stance, damage and wreck states below the first hit,
  vehicles that only exist in a level's script (carriers' deck traffic,
  ship-to-ship fire).
* **Anything the install does not contain.** A texture or sound absent from the
  retail archives is accepted with evidence (retail draws it untextured or
  silent too); the framework cannot tell a content gap in the mod from a bug in
  the viewer where the game itself degrades.
* **A gate that is wrong.** The audits are written against known defects. A
  new defect class passes until someone finds it and adds a check; add it to
  `REGRESSION_CORPUS` the day it is fixed.
* **Publishing.** Nothing here looks at the cluster or the published tree.
