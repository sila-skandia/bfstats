# Mods in the mesh viewer

The extraction pipeline in `tools/bf1942-models/` has always taken `--mod`; what
it did not have was anywhere to put a second game's output, or a way for the
viewer to find it. This adds both, piloted on **Eve of Destruction 2.50**.

Vanilla does not move. `models/`, `maps/` and `models/poses/` are exactly where
they were, because that tree is what `upload-mesh-assets.sh` has already pushed
to the PVC.

## The tree

```
viewer/
├── models/                       # vanilla — unchanged
│   ├── mods.json                 # the registry; generated
│   ├── models.json  damage.json  *.glb  *.report.json
│   ├── thumbs/
│   └── poses/                    # poses-matrix.json  *.pose.glb
├── models/mods/eod/              # one mod, same shape
│   ├── models.json  damage.json  *.glb  *.report.json
│   ├── thumbs/
│   └── poses/
├── maps/                         # vanilla — unchanged
│   ├── maps.json
│   └── <level>/scene.glb …
└── maps/mods/eod/
    ├── maps.json
    └── <level>/scene.glb …
```

Two properties made this the shape to pick, over a single merged manifest with a
`mod` field on each row:

* **No extractor needs a new flag.** Every script already writes its manifest
  into `--out`, so a mod is `--mod EoD --out viewer/models/mods/eod` and
  `models.json` lands *inside* that directory, written by the same code that
  writes vanilla's. A merged manifest would have meant teaching three extractors
  to read-modify-write a shared file, and to not clobber another mod's rows.
* **Publishing stays a per-tree upload.** `viewer/models/mods/eod` and
  `viewer/maps/mods/eod` are each self-contained, so pushing EoD is the existing
  recursive upload aimed one directory deeper. Nothing about the vanilla upload
  changes, and a mod can go live without re-uploading 94 vanilla models.

The rows already carried `"mod": "<name>"` before any of this; that field is
still written and is now redundant with the directory, which is fine — it says
which archives a row came from, which a path only implies.

### `models/mods.json`

Generated by `build_mods_manifest.py`, which scans the two asset roots:

```json
{ "mods": [
  { "id": "bf1942", "name": "Battlefield 1942", "short": "BF1942",
    "paths": { "models": "models", "maps": "maps", "poses": "models/poses" },
    "counts": { "models": 94, "maps": 23, "poses": 224 } },
  { "id": "eod", "name": "Eve of Destruction", "short": "EoD",
    "paths": { "models": "models/mods/eod", "maps": "maps/mods/eod",
               "poses": "models/mods/eod/poses" },
    "counts": { "models": 11, "maps": 2, "poses": 32 } }
] }
```

It sits **inside `models/`, not at the viewer root**, and that is load-bearing.
`mesh/Dockerfile` copies all of `viewer/` into the image and then deletes
`models/` and `maps/`, which `mesh-deployment.yaml` remounts as PVC subPaths. A
registry at the viewer root could therefore only change on an image build, while
the thing it describes changes on an upload. `models/` is the mount both the
Models and the Poses tabs already read, so the registry rides along with the
models upload.

`counts` is the whole reason this file is generated rather than hand-written.
Uploads happen per tree and land at different times, so a mod is routinely
present on one tab and absent from another. The count is what the picker
filters on, so **EoD does not appear in the Maps dropdown until
`maps/mods/eod/maps.json` exists on the volume** — which is exactly the state
production is in today, with no EoD assets uploaded at all.

Re-run it after any extraction:

```bash
cd tools/bf1942-models && python3 build_mods_manifest.py
```

## The UI

`viewer/mods.js` is shared by all three pages. Each one resolves a base path at
module scope before it fetches anything:

```js
const activeMod = await selectMod('models');
const MODELS_BASE = activeMod.paths.models;
```

Every asset URL those pages already built keeps its shape and just hangs off the
base. `selectMod` also injects the picker into `.shell-nav` (styled in
`shell.css` as `.shell-mods`, matching the tab bar) and rewrites the Models /
Maps / Poses links to carry `?mod=`, so the choice survives a tab change. It is
also kept in `localStorage`, and changing it reloads the page — all three pages
resolve their manifest once with top-level await, and a reload is the honest way
to re-enter that.

Three degradations it has to survive, all of which production will hit:

| Situation | Behaviour |
|---|---|
| No `models/mods.json` (tree uploaded before this existed) | fetch fails, vanilla's classic paths returned, no picker drawn |
| Only one mod has assets for this tab | picker not drawn at all — the page looks as it always did |
| `?mod=` names something this tab cannot serve | falls back to vanilla rather than fetching a 404 manifest |

## Mod-specific things that had to be fixed

Four, of which only the last is really about EoD rather than about mods in
general.

**1. Level archives were looked up in a folder named after the mod.**
`find_level_archives` searched `Archives/<modname>/levels/`, which is right for
vanilla by coincidence — the mod *is* called bf1942 — and wrong for every mod.
Levels always live in `Archives/bf1942/levels/`, because Refractor mounts an
archive at its own internal path prefix and level archives all start `bf1942/`.
Now uses `rfa.find_levels_dir`, the helper that already documented this.

**2. Level lookup did not follow the mod chain.** It now takes the chain and
searches the parents too, placing their archives *first* so the nearest mod
still wins in `LevelFiles`. That is the underlay the engine gets free from
`addModPath`: a mod map that ships only `Init.con` and
`ObjectSpawnTemplates.con` resolves `Terrain.con` and the heightmap from the
parent's copy of the same level. EoD's two maps did not need it — both are
complete — but any DC or FH map will.

**3. A damaged archive entry aborted the whole extraction.** EoD's
`objects.rfa` has three entries whose LZO streams overrun their lookbehind
window (`e_MuzzSG44/Geometries.con` and two Rocketlauncher `.ssc` sounds, out of
4806 entries) — the shipped archive is simply corrupt there. `build_library`
read every `.con` with a bare `pool.read`, so one bad effects script took the
mod down with `ValueError: lzo1x_decompress_safe returned -6`.
`ArchivePool.try_read` now warns once and returns `None`, and the two bulk `.con`
scans use it. Log and skip, don't 500 the list.

**4. `ObjectTemplate.geometry` can name a template the mod never declares.**
EoD's `M79` points at a geometry called `M79` that exists nowhere in its
archives. `weld_metrics` dereferenced `library.geometry(name).mesh_file` before
its own `is None` guard ran, so the pose matrix crashed on it. The engine draws
nothing for a dangling reference; named-but-unknown now reads the same as no
geometry, and `M79` exports a pose with no weld metrics instead of taking the
run down.

Two additive CLI conveniences went in alongside: `extract_pose.py --matrix` now
accepts `--soldiers` / `--weapons` (EoD declares 77 stand-aim weapons against
vanilla's 28, so the full 19x77 product is not a sample), and `shoot.mjs
--thumbs` takes `--manifest` so it can stamp a mod's `models.json`.

Nothing above is EoD-only in the code. There are no `if mod == "eod"` branches.

## What a full EoD rollout would involve

1. `python3 extract_all.py --mod EoD --out viewer/models/mods/eod
   --configuration-all --verify` for all 284 templates. Skip `--level-all`: it
   is 239 level archives probed per template and it is what turned the first
   sample run into a multi-hour job for no gain — EoD ships almost no per-level
   vehicle reskins, so every variant printed "no matching vehicle textures".
2. Pick maps deliberately rather than extracting all 237. Each one is ~30 MB of
   `scene.glb` plus lightmaps; the full set would be several GB against a PVC
   shared with everything else on a single 7741Mi node.
3. `node shoot.mjs --thumbs --url http://localhost:5273/?mod=eod --out
   viewer/models/mods/eod/thumbs --manifest viewer/models/mods/eod/models.json`
4. `python3 build_mods_manifest.py`
5. `./scripts/upload-mesh-assets.sh`. It walks each tree recursively, so
   `models/mods/eod/`, `models/mods/eod/thumbs/` and `models/mods.json` all ride
   along with the models half and `maps/mods/eod/` with the maps half — no new
   flags.

   **Order matters, because `mods.json` goes up inside the models tree.** Run
   `--maps` first and `--models` second: the registry is what makes a mod
   visible, and landing it before `maps/mods/eod/` exists would put EoD in the
   Maps dropdown pointing at nothing. Publishing models before maps are ready is
   fine on purpose — regenerate with the maps tree absent and `counts.maps` is
   zero, so the Maps tab simply does not offer EoD until it is there.
