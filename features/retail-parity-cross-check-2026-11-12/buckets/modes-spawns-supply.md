## Findings (non-MATCH), most severe first

### F1 [CODE-WRONG] [medium] An attacker alone on an owned point with a spent lose timer never takes it (state-2 gate applied where retail has none)
- Code: tools/bf1942-models/viewer/control-point-law.js:168-181 — `losing` = `if (cp.lose > 0) {...} if (cp.state !== 2) return null; cp.state = 1; ... flag.team = 0`; used for the attacker-alone branch at :188 `if (owner) return losing(attacker);`
- Ledger: AI-100 ("attackers on an owned point -> losing / lost") does not state the gate either way; FHR-1 is about the nobody branch only.
- Third-party: not needed; read straight from our binary.
- Our binary (lnxded.static, `ControlPoint::handleFrameUpdate` 0x08283b00): the attacker-alone branch on an owned point is
  `8283c18 flds 0x168(%edx); fldz; fucompp; testb $0x1,%ah; jne 0x8283c31` (lose > 0 -> `losingControl(attacker,dt)`), else
  `8283c29 movl -0x44(%ebp),%esi; push edi; push edi; push esi; jmp 0x8283be3` -> `call lostControl` — **no `cmpl $0x2,0x17c(%edx)`**.
  The state-2 test exists only in the nobody branch (`8283bd2 cmpl $0x2,0x17c(%edx)`) and the defended+enemy branch (`8283ddb cmpl $0x2,0x17c(%edx)`). `lostControl` 0x08284090 itself tests only `+0x214`.
- Verdict reasoning: in the code a point whose lose timer starts at or below 0 (state 4 from `control`) is never lost to a lone attacker; retail loses it on the first frame. Data: bf1918 `fao_landing` `Fao_Beach` (one mode: team 2, `timeToLoseControl 0`, `timeToGetControl 0`) — retail flips it in two frames, ours never does. Elsewhere (lose timer > 0) the results agree, because losingControl always leaves state 2.
- Fix: give the attacker-alone call its own path: in `controlPointStep`, replace `if (owner) return losing(attacker);` with a call that skips the state test (e.g. `losing(attacker, /*gate*/ false)` where `losing(team, gate = true)` does `if (gate && cp.state !== 2) return null;`). Keep the gate for the defended branch (:183) and the nobody branch (:212). Pin in `tests/test_control_point_law.py` (lose 0, owned, one attacker -> `{lost}` on frame 1). The one copy feeds the bot referee (solo play), the capture-ring estimate (capture-rings.js) and the lab checks, so the fix lands in all three.

### F5 [CODE-WRONG] [low] A depot's 0.5 s cycle fires at exactly 0.5 s here; retail needs strictly more, and starts each depot at a random phase
- Code: tools/bf1942-models/viewer/supply.js:229-233 / `step`: `if (this._elapsed < UPDATE_INTERVAL) return null;` and `this._elapsed = 0` at construction.
- Ledger: SUP-4 (threshold `+0x1e8` 0.5, `+0x154` seeded `(rand()%30)/30.0`) — states the phase; is silent on the comparison.
- Our binary: `SupplyDepot::handleUpdate` 0x083240f0: `fldl 0x87435a0` (world time) minus `flds 0x154(%ebx)`, `flds 0x1e8(%eax)` (0.5, `SupplyDepotTemplate` ctor `832516e movl $0x3f000000,0x1e8(%ebx)`), `fucom; testb $0x45,%ah; je 0x8324128` -> `update` only when elapsed > 0.5; `<=` returns.
- Verdict reasoning: at a fixed 1/30 s step the viewer cycles every 15 steps (0.5 s) where retail's world-time difference has to exceed 0.5, so 16 steps (0.533 s) whenever the sum lands on 0.5. The heal is `rate x elapsed` so HP/s is unchanged; ammo bucket units and FH killer depots' fixed `-10 per cycle` repair rows (SUP-11) run ~6% faster here. Low.
- Fix: `if (this._elapsed <= UPDATE_INTERVAL) return null;` and seed `this._elapsed` with `(Math.floor(Math.random()*30))/30` (or a deterministic per-depot phase) to mirror the ctor's `(rand()%30)/30`.
