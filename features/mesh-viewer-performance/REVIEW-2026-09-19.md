# Performance review — map page, 2026-09-19

A code smell review of the map page's on-foot hot path (`tools/bf1942-models/viewer/`),
driven by Dylan's report that prone and firing feel laggy and that it has got worse
recently. Method: static pass over the per-frame path plus orchestrated headless
Chromium measurements (`perfbench.cjs` stepped phases, CDP profiler probes under
`?shots`). Probe scripts live at `/tmp/kilo/probe.mjs` (first-trigger / reheated burst /
prone-while-firing / prone-only) and `/tmp/kilo/geom-probe.mjs` (warm-up coverage on
the first shot).

## Measurement caveats

Today's box ran at load 10-31 (other sessions' background load), so absolute
frame times are not comparable to the perf pass's numbers — **read workload
counters and shapes, not ms, below**. Page load itself took 307 s on one run.

Key workload facts:

- **first-burst-4s is a regression against the perf pass.** The final perf-pass build
  measured 1/238 frames over 33 ms with max 33.3 ms for the burst opening; today it is
  50-55/117 with a 266-983 ms worst frame. Programs stay flat (30 → 30) and textures
  flat, so this is **not** rule 6 reopening — the worst frames carry `particles: 0`
  and only 3-6 shots, so it is not the effect pools either.
- **The sim-tick catch-up amplifier.** The soldier body's `FixedStep` runs whole 60 Hz
  ticks to pay off the frame's worth of sim time (`soldier.js` `step`, `clock.advance`).
  Probe A caught a frame whose 433 ms carried **210 ticks and 24 collider casts**; the
  running-tense profile showed 4-16 casts/frame standing still. A single slow frame
  therefore owes several frames of physics in the *next* frame, which is slow again —
  one hitch breeds a small burst. The physics wave this lives in landed 2026-09-15..20,
  five days before this review — the "worse recently" window.
- **Prone is not a JS-side cost.** Probe C/D: the stance toggle itself, the eye ease,
  and the first fired rounds while prone all pace identically to standing; prone's
  capsule is one sphere vs standing's three. If prone *feels* worse, the remaining
  suspect is GPU fill overdraw: prone eye is 0.44 m with `camera.near = 0.2`
  (`map.html:6201`), so the terrain fills the whole view at a grazing angle under the
  0.1 m near pass — MSAA (`?aa=0`, `?dpr=` exist to test this) and the fill rate scale
  with screen coverage, which is exactly what does not show in JS counters.
- **Warm-up holds for the muzzle flash and fire clip** (first 3 shots add zero
  geometries), but the tracer strand pools miss 2-6 clones per first burst (`gunfire.js`
  `#spawnTracer`, geometry +6/+2 across the runs) — a pool-size question, not a
  warm-up gap.

## Findings, by impact

### F1. No cap on sim-tick debt — the hitch multiplier
`soldier.js:472` `clock.advance(frameDt)` pays back all lost sim time; a 300 ms stall
after a GC/sharder/load hiccup is 18 ticks of full physics (4-24 casts each) owed to
the following frames. This turns any occasional slow frame into a run of slow frames,
and it is the one mechanism on the on-foot path that is new since the perf pass's
`93105a2`/`53f420d` measurements. Suggest a **tick cap** (the engine's own
`g_simulationFps` clamp: drop debt beyond ~2-3 ticks, or clamp the accumulator) —
frame-rate independence for a healthy machine, no compounding on a sick one. Needs a
behaviour decision (replay determinism: `replays/` records input streams and replays
them through the same fixed-step clock, so the cap must live beside the clock, not
after it).

### F2. Unconditional `camera.updateProjectionMatrix()` every on-foot frame
`map.html:8012-8013` sets `camera.fov` and recomputes the projection matrix on every
frame of every life, even when the FOV has not moved for minutes. Every other mode
guards this (`map.html:10456` `camera.fov !== MANNED_GUN_FOV`). An invert + matrix
chain is microseconds, but it is also free to guard: `if (camera.fov !== hw.worldFov)`.
The `fovCur`/`worldFov` eases already snap to target, so the compare turns false for
most frames the moment the ease settles.

### F3. Tracer strand pools are undersized for an on-foot first burst
`gunfire.js:686-707` — the baked-streak pool (`group.tracerMeshPool`) and the shared
cylinder `tracerPool` are populated with one mesh each at warm-up, and a Thompson's
opening burst (4 tracers/s, 1.5 s TTL) exhausts them; the misses clone (`clone()` +
geometry upload) mid-burst. The perf pass's rule 6 guarantee is "nothing links or
uploads during a real burst" — the strand mesh is the one node that still does.
Suggest sizing the pools to `ceil(roundOfFire / tracerInterval * timeToLive) + 2`
per group at warm-up.

### F4. Per-frame allocations on named hot paths
- `map.html:2929` `[obj.material].flat()` per fade mesh per frame in
  `updateTextureFade` — Wake binds a few hundred `textureFade` trees; that is a few
  hundred tiny arrays / frame of GC churn. `isArray(m) ? m : [m]` indexing or a cached
  material ref removes them.
- `map.html:6359` a fresh `input` object per `onFoot` frame — harmless (escaping
  pressure keeps it cheap) but trivially hoistable like `footEye`/`supplyTarget`
  already are.
- These are small; they are listed because the module is otherwise scrupulous about
  rule 5 and they are the only survivors.

### F5. Audio per-shot graph churn
`map.html:7871-7889` `playHandFire`: two WebAudio nodes + a connect + an `onended`
closure allocated and torn down per round. Fine at the Thompson's 11.6/s, but it is
the only per-shot allocation in the burst path and it scales with everything
auto-fire will add. A pooled pair of source/gain nodes per weapon is the obvious shape
if weapon audio ever shows up on a profile.

## What is NOT the problem (checked, so nobody re-hunts it)

- **Shader/program warm-up (rule 6):** programs flat 30→30 and textures flat 352→352
  across every burst today; the first three single shots added zero geometries.
  The Decal-opaque regression that reopened rule 6 stays closed.
- **Effects/pools while firing:** worst burst-opening frames carry `particles: 0`;
  `effects.advance` and the gunfire pools are unchanged from the perf pass's final
  numbers (draw calls 187-191 on-foot, up to ~1,460 only while panning).
- **The near pass / 1P FOV change** (`vmCamera.near = 0.1`, `set1pFov` default,
  `9b67edd`): draw-call counts are unchanged by it; if it hurts at all it would show
  on the GPU-fill side (see prone note above), not in JS.
- **DOM reads forcing layout (rule 3), matrix walk of statics (rule 2), map repaint
  gate (rule 7):** all hold — nothing on those hot paths allocates or walks
  unexpectedly today.

## Open item that needs a quiet box

The 266-983 ms single frame at trigger-pull, with flat programs/textures and no
particles, is still unattributed: `(program)` (unresolved/native) was 89% of probe A's
profile at load 30, and the one clean signature (210 ticks/24 casts) is the F1
amplifier, not a cause. On a quiet machine, re-run `perfbench.cjs bench --realtime 0`
and read the `first-burst-4s` `longest` rows — if the 200 ms+ frame survives with
casts ≤ 8, the cost is off the page's JS (GL/driver/audio context resume) and deserves
its own pass with `--gpu-timer`.

## Tooling note

One harness bug surfaced while measuring: `perfbench.cjs` crashed in `pacing()` on an
empty realtime frames array (`--realtime 0`, the documented "skip the realtime phase"
switch). The guard is `6c0cafe` (`fix(mesh): perfbench pacing guards an empty frame
capture`), merged into main while this review was in flight — same fix I re-derived
independently mid-review, and the worktree came out clean for it.
